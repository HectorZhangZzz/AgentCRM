# GitHub 源码版本备份

GitHub 保存程序版本：代码、Skill、部署与使用说明、合成示例和锁定依赖清单。客户数据库、原始附件、访问凭据和私有备份继续保存在本机；它们需要另外执行完整私有备份，不能靠克隆 GitHub 恢复。

## 准备净化源码快照

在实际项目根目录运行：

```bash
python3 ops/github_backup.py prepare
```

工具复用源码分享的允许目录和排除规则，在 `.local/github-source/` 创建独立的 Git 仓库。它使用新的源码历史，保留原项目及其现有 Git 历史，不推送原项目的旧提交。未知目录、未提交改动或异常的管理标记会阻止覆盖。

除 `.local/`、客户资料、备份、依赖和运行时二进制外，还排除了来源不明的上游会议调试文件 `vendor/twenty/packages/twenty-companion/test.json`、遗留 `.bak-*` / `.before-*` 配置副本和本机验收结果。原上游文件继续保留在本机，运行中的服务不受影响。原始桌面 `twenty.zip` 含旧配置和凭据，不能原样上传。

`prepare` 不连接 GitHub，不读取 GitHub 令牌，也不上传。新的源码快照是便于重建的源码版本，不是可直接运行的数据库镜像。

## 优先使用现有 GitHub 连接器

当前目标是已核验为私有的 [HectorZhangZzz/AgentCRM](https://github.com/HectorZhangZzz/AgentCRM)。2026-10-28 已用现有 GitHub 连接器完成首次完整源码备份：[提交 1264bec](https://github.com/HectorZhangZzz/AgentCRM/commit/1264beccfd2081c790b1df9c180eab15c7f6a1b0)，共 21,231 个文件，服务端完整树 SHA 与本地净化快照一致，且已回读核对当时的 `main` 提交。后续修订继续形成新提交，当前版本以最新 `main` 及其校验记录为准。

继续使用当前已连接的 GitHub 工具即可，不要求为了上传再登录 GitHub CLI。当前连接器提供已有仓库的对象、提交和分支操作，但没有 `create_repository` 工具；建库能力与账号的全库授权是两回事。本仓库已经由用户创建，无需再次建库。不要读取其他程序的凭据补充工具能力。

上传来源只使用 `prepare` 生成的净化快照，不能直接推送原项目的旧历史。使用连接器时按以下顺序操作：

1. 读取仓库可见性和目标分支当前提交；有已有内容时先审查，避免覆盖其他人的改动。
2. 根据净化快照建立完整文件清单，比较远端路径和 Git 对象 SHA，仅为新增或内容变化的文件调用 `create_blob`；未变化的对象直接复用。
3. 用预期的完整文件清单调用 `create_tree`，正确处理删除的路径；不要把一次增量列表误当最终完整目录。
4. 调用 `create_commit`，以刚核对的分支当前提交为父提交。当前工具需要父提交，空仓库应先用 `create_file` 写入说明文件建立初始分支，再创建完整提交。
5. 更新分支前复核分支头，使用普通、非强制的 `update_ref`；工具支持预期旧提交或租约参数时一并使用。分支已变化或更新被拒绝时，重新读取并协调变更，不强制覆盖。
6. 回读远端分支和提交，核对分支头。将服务端 `create_tree` 返回的完整树 SHA 与本地预期 Git 树 SHA 比对，或完整读取路径和对象 SHA 后核对。读取树响应被截断时须逐层读取，不能把部分结果当全量验证。

仅创建 blob、tree 或 commit 都不足以完成备份。只有目标分支已指向新提交，且完整文件树与净化快照一致，才能记录仓库地址和远端提交为成功结果。

## GitHub CLI 后备方式

连接器确实无法完成所需操作时，再考虑官方 GitHub CLI。连接器的认证不等于系统 Git 或 CLI 已登录；已有连接器可用时不必另走这条授权流程。可使用 PATH 中的 `gh`；本机准备的副本在 `.local/tools/github-cli/usr/bin/gh`。确需首次 CLI 授权时，由本人按[官方说明](https://cli.github.com/manual/gh_auth_login)完成，不将密码或令牌粘贴到聊天或项目源码。

对于一直通过 CLI helper 维护、历史一致的快照，可执行：

```bash
python3 ops/github_backup.py publish --repository HectorZhangZzz/AgentCRM
```

工具核对登录账号，只在明确不存在时创建私有仓库，拒绝推送到已有公开仓库；使用常规 Git 推送并核对远端提交，不执行强制覆盖。

**连接器创建的远端提交与 `.local/github-source/` 的本地快照提交可能具有不同 SHA 和历史。** 从连接器切换到 CLI 前，必须先 fetch 远端，审查并协调两边历史，再进行普通推送；不能直接假定 helper 的本地提交就是远端提交，也不能用强制推送解决分歧。

## 后续更新

先在实际项目修改、检查、提交，再运行 `prepare`。优先用现有连接器按上述流程同步，仅上传变化的 blob，仍然构造并验证完整树；继续走 CLI 时须先确认历史一致，再运行 `publish`。快照仓库只负责同步经过筛选的源码，不在其中录入客户资料或做日常开发。不要在原项目根目录添加远端后直接推送旧 `main`，以免将历史里的上游调试资料一起发出。

远端出现其他人提交时，普通推送会拒绝覆盖；应先审查并合并变更，再同步新版本。没有定时任务自动推送，也不自动开放仓库给朋友。仓库访问范围扩大或改为公开须由本人另外决定。

第三方源码保留原许可。`vendor/twenty/LICENSE` 同时描述 AGPLv3 和带 `@license Enterprise` 标记文件的商业许可例外，不能把整个项目重新声明为 MIT 或统一开源许可。
